## Interpretation so far
Cost = (#MBs entering unified sub-partition search) x (per-search SATD cost).
Divergent content pushes 58% of Phase2 MBs into unified search vs 8% on coherent content.
SubPartBudget = SliceMbCount/4 = 510/slice = 2040/frame; unified MBs/frame = 505 (~126/slice)
-> the budget NEVER BINDS on this content. It caps a pathological 100%-of-MBs case at 25%,
   but 25% of MBs at ~300us each is already ~60ms/frame of thread work. (VERIFY semantics.)

## SubPartBudget semantics (H264BaselineSliceEncoder.cs:1893-1896)
_subPartMbCount++ for EVERY Phase2 MB with variance>=64 (whether or not unified search runs);
over budget => rangeCapThisMb = min(4, cap). That is all it does. It bounds nothing else.
On div content: ~505 unified MBs/frame ~= 126/slice vs budget 510/slice -> never binds.

## Effort-counting fix (commit "count atlas/transform-domain/bounded SATD candidates")
ThreadSearchEffort was blind to the default-config hex path (SatdBlockFromReferenceAtlas /
SatdBlockBounded / SatdBlockTransformDomain). After fix: default 1.166M units/frame (143/MB),
div 5.63M (690/MB), hot row 1.51M (12.5K/MB). Effort tracks thread-time at ~35 ns/unit on
both contents. Frame time unchanged (13.0 / 83.5 ms).

## MotionSearchEffortCapPerMb: deterministic per-slice budget + degradation ladder
Budget/slice = cap x frameMbCount / sliceCount (EQUAL share, not slice-MB-proportional: the
effort balancer gives hot bands fewer rows, so a proportional budget binds on exactly the slice
the balancer already equalised — measured as spurious tier engagement on coherent content).
Ladder at 50/75/100% consumed: (1) skip 65x65 exhaustive fallback, subpart radius<=8;
(2) + drop ref1, window 16, radius<=4; (3) 16x16-only, window 8.
Consumption = slice's own ThreadSearchEffort delta -> bitstream independent of scheduling/clock.
